mlx

mlx

Run models on Apple Silicon with mlx-lm, with a prompt cache rishi manages itself, speculative decoding, a quantized KV cache, and vision and audio through mlx-vlm.

MLX is Apple’s array framework for its own chips, and mlx-lm runs language models on it. This backend needs an Apple Silicon Mac and pip install 'rishi[mlx]'. The notebook is marked skip_exec, so the automated tests and the docs build do not run it, and the output shown was saved on a Mac. Behaviour shared with every backend is on the index page and in Urai.

Loading models

MLX models are Hugging Face repos of quantized weights, most of them under mlx-community. A LiteRT-LM model is one .litertlm file and a llama.cpp model one .gguf file, but an MLX model is a whole directory. mlx_lm.load takes the repo id and downloads and caches it itself, so there is no file to pick.

Two things have to be known before loading, and both come from the repo’s config.json, which read_config reads from a local directory or the Hub. It returns {} when the file cannot be read. One is the context window, which ctx_len reads, 8192 when the config does not give one. The other is whether the model has a vision or audio tower, a second network that encodes pictures or sound for the language model; is_vlm checks for one. A model with a tower needs mlx-vlm instead of mlx-lm. cached_models lists the repos in the local Hugging Face cache whose ids contain mlx, without using the network. MlxEngine holds a loaded model, its tokenizer and an optional draft model.

The prompt cache

The KV cache holds the keys and values computed for tokens the model has already read, so a prompt that starts the same way as the last one does not have to be read again. LiteRT-LM keeps that state inside its conversation object, and llama.cpp finds the longest matching prefix on its own. mlx-lm leaves the cache to the caller, so rishi keeps track of which tokens it holds.

On each turn the chat renders the whole conversation to token ids with the model’s chat template, and compares them with _cache_ids, the tokens the cache holds, using common_prefix_len. Everything up to the first difference is already cached and is skipped. Everything after it is stale. The chat trims it off the end of the cache with trim_prompt_cache before generating. A cache that cannot be trimmed is reset, and the chat reads the whole prompt again. mlx-lm’s own server reuses a cache between requests the same way.

Stale tokens do turn up. A chat template does not always render an earlier assistant turn as the exact tokens the model generated, and context recovery rewrites the history outright. Comparing tokens instead of trusting the cache handles both cases. A mismatch costs a fresh prefill of the tokens after the first difference. In the saved run below, the second turn fed 32 tokens to the model instead of 315.

MlxChat

MlxChat has the same interface as every other backend. max_output_tokens defaults to DFLT_MAX_TOKENS, 1024. When the repo’s config declares a vision or audio tower, MlxChat(...) returns an MlxVlmChat. Pass vlm=True or vlm=False to override that check. Its own options are these:

  • kv_bits stores the KV cache quantized to that many bits. This saves memory on long contexts. Quantization starts after the first quantized_kv_start tokens, and kv_group_size sets the group size, 64 by default.
  • draft_model names a small model for speculative decoding. The draft model guesses several tokens ahead and the main model checks them in one pass, which is faster when the guesses are good. The chat then keeps a cache for both models.
  • adapter_path applies a LoRA adapter.
  • prompt_cache=False turns the cache off, and max_kv_size caps its size.
  • min_p sets a sampling threshold. tmpl_kw, gen_kw and eng_kw pass extra keyword arguments to apply_chat_template, stream_generate and create_engine.

save_cache and load_cache write the cache to a file and read it back. save_cache raises ValueError when prompt_cache=False. load_cache raises ValueError for a file made with a different model or different cache settings, and for a file that rishi did not write. chat.use.cached_tokens reports how many prompt tokens each turn reused.

Vision and audio

mlx-lm reads text only. Images and audio go through mlx-vlm, which builds on mlx-lm and adds the vision and audio towers. Install it with pip install 'rishi[mlx-vlm]'.

You do not have to pick the class. MlxChat(repo) reads the repo’s config.json and returns an MlxVlmChat when it finds a vision or audio tower. Chat('mlx-community/Qwen3-VL-4B-Instruct-4bit') works as it is. Pass vlm=True or vlm=False to decide yourself.

MlxVlmChat changes only loading, prompt building and the generate call, and inherits the history, callbacks and tool loop. It has two limits. mlx-vlm has no per-model tool-call parsers. Tool calls work only with models that write <tool_call> tags, and not every vision model does. mlx-vlm also keeps its own cache of image features instead of a token KV cache. Prompt reuse between turns is off on this path. Images must be bytes or local files. A remote image URL raises ValueError.

Audio takes the same path. Give a Path or bytes to a model with an audio tower, and mlx-vlm decodes it and resamples it to the rate the model expects. One setting is rishi’s rather than mlx-vlm’s: thinking. By default mlx-vlm asks the chat template for enable_thinking=False, which inserts an empty <think></think> block. A model told it has finished thinking can end its turn at once. Qwen3-Omni then transcribes nothing. rishi passes its own think setting instead. With the default think=None, the model’s chat template decides.

Sharing one engine

MlxBroker keeps one loaded MLX model in a long-lived process and serves an MlxChat to each client over a Unix socket. All clients share the weights, and each has its own prompt cache. The protocol is Urai’s ChatBroker, described on Urai’s broker page.
