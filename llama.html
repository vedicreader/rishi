Loading GGUF models

Any GGUF repo on the HuggingFace Hub works; the Qwen3 and Gemma 3 ids below are handy defaults (Qwen3 gives you thinking and Hermes-style tool calls out of the box). get_model resolves a .gguf file with the same cache-first ladder as rishi.core.get_model: explicit model_path, then the local HF cache (no network), then a download - preferring the requested quant and skipping mmproj projector files. get_mmproj is the complement: it resolves the projector itself the same way, for vision models.

Audio

llama-cpp-python’s MTMD handler only wired images upstream. rishi @patches four MTMDChatHandler methods so audio follows the same path: collect input_audio parts, collapse string templates for Llama/Voxtral, decode with read_audio (libsndfile), and feed mtmd_bitmap_init_from_audio.

The KV cache

llama.cpp manages this itself, and rishi gets it for free by holding one Llama across turns: Llama.generate compares the incoming prompt against the tokens already in the context, trims the KV cache to the common prefix, and evaluates only the tail. Because history grows by appending, each turn is an extension of the last, so an ordinary conversation re-prefills nothing.

Three things break that prefix, and rishi knows about all three, which is what cached_tokens reports:

  • A one-shot on the same engine. A Llama has a single context, so classify, structured, check and grades overwrite the conversation - the next real turn re-prefills from scratch. Same for two Chats sharing one engine=, and for a judge= chat on the same engine. preserve_cache=True saves and restores the llama state around one-shots instead; it copies the whole KV cache, so it only pays off when a re-prefill would cost more than the copy.
  • A rewritten history. SlidingWindowCallback eviction and context recovery both change the middle of the conversation, so everything after the first changed message is re-evaluated. Keep keep_first small.
  • Media. The live turn carries the real image or audio, but on later turns it is replaced with an [image]/[audio] placeholder so it isn’t re-encoded. That is deliberate, and it means a turn containing media forces a re-prefill on the next one, from that message onward.

save_cache/load_cache persist the whole context to disk, the same API rishi.mlx exposes, so a long system prompt can be prefilled once and reused in later sessions.

Below: llama-only behavior — KV prefix reuse and mmproj multimodal.

# Real llama.cpp KV-prefix test: instrument `eval` to see how many tokens are actually evaluated.
# On turn two the first eval batch should contain only the new tail, not the cached conversation.
kvchat = LlamaChat(qwen3_06b, think=False, temp=0.0, max_output_tokens=16)
seen, orig_eval = [], kvchat.engine.eval
def counted_eval(tokens):
    seen.append(len(tokens))
    return orig_eval(tokens)
kvchat.engine.eval = counted_eval
try:
    kvchat(('cache verification context ' * 96) + '\nReply with exactly: stored')
    context_before_turn2 = kvchat.engine.n_tokens
    seen.clear()
    r = kvchat('What exact word did I ask you to reply with? Reply with only that word.')
    assert seen, 'llama.cpp never evaluated the second prompt'
    second_tail = seen[0]
    print(dict(context_before_turn2=context_before_turn2, second_tail_evaluated=second_tail,
               reported_cached=kvchat.use.cached_tokens, answer=resp_text(r)))
    assert second_tail < context_before_turn2, 'turn two re-evaluated the full prior context; KV prefix reuse missed'
    assert kvchat.use.cached_tokens > 0, kvchat.use
    assert 'stored' in resp_text(r).lower(), resp_text(r)
finally:
    kvchat.engine.eval = orig_eval
    kvchat.close()

Streaming and thinking

stream=True yields markdown chunks (thinking streams as a blockquote, tool calls as ⏳ lines) - render live with display_stream, exactly like the litert backend. With a Qwen3 model, think=True turns the thinking channel on.

Stopping with an LLM judge

done is any chat -> bool, so instead of output_matches (a substring check on the last code output) you can let a model decide when the loop is finished. The built-in task_complete judges - via chat.classify, isolated - whether the conversation has satisfied the request. Or write your own done that closes over a judge Chat (pass a stronger model as the judge if you like), mirroring output_matches’ factory shape. This is backend-agnostic - the same done works with the litert Chat.
