# AGENTS.md

## Cursor Cloud specific instructions

`rishi` is an [nbdev](https://nbdev.fast.ai/) Python library: a thin `Chat` layer over four
LLM backends (litert, llama.cpp, mlx, remote) plus a cursor-agent backend. It is a library, not a
web service — "running the app" means importing `rishi` and driving a model through `Chat`.

### Source of truth
- The notebooks in `nbs/` are the source. The `rishi/*.py` files are AUTOGENERATED — never edit them
  by hand. Edit the matching notebook and run `uv run nbdev-export`.

### Environment / dependencies
- Managed with `uv` (see `pyproject.toml` `[dependency-groups]` and `[tool.uv]`). The startup update
  script runs `uv sync`, which creates `.venv` and installs the `dev` group (which pulls `rishi[all]`).
- On Linux the `mlx`/`mlx-vlm` extras are skipped via platform markers, and `llama-cpp-python` installs
  the CPU wheel from the configured `llama-cpu` index. So `rishi.mlx` won't import here; that's expected.
- Run tooling through the venv, e.g. `uv run <cmd>`. nbdev console scripts are HYPHENATED
  (`nbdev-export`, `nbdev-test`, `nbdev-prepare`, `nbdev-clean`), not underscored.

### Lint / consistency
- `uv run nbdev-export` then `git status` — a clean tree means notebooks and exported `.py` agree.
  `uv run nbdev-clean` strips notebook metadata. (Equivalent to what CI's nbdev workflow checks.)

### Tests
- `uv run nbdev-test` executes every notebook. Most pass offline: model calls are served from a
  record/replay cache (`RecordCache`, backed by `diskcache`) rather than hitting real models.
- Two notebooks fail in a bare environment for external reasons, NOT code bugs:
  - `05_cursor.ipynb` needs the `cursor-agent` CLI on `$PATH` (install the Cursor CLI and
    `cursor-agent login`); even listing models shells out to it.
  - `index.ipynb` has a live chat cell that needs either a committed recording or
    `RISHI_RECORD_CHAT=1` plus a real backend/API key.
  To record fresh fixtures, set `RISHI_RECORD_CHAT=1` and re-run with a working backend.

### Running a real model with no API key
- The keyless, self-contained path is the llama.cpp backend with a small GGUF. Example:
  `from rishi.core import Chat, resp_text; chat = Chat('Qwen/Qwen3-0.6B-GGUF', n_ctx=2048); print(resp_text(chat('hi')))`.
  The weights download once from the HF Hub (no token needed, just slower/rate-limited) and are cached;
  inference runs on CPU.
- The `remote` backend needs provider keys (e.g. `ANTHROPIC_API_KEY`/`OPENAI_API_KEY`/`GEMINI_API_KEY`)
  and the `cursor` backend needs the `cursor-agent` CLI — neither is configured by default.

### Gotchas
- `Chat(...)` takes generation options like `think`, `temp`, `top_k`, `seed` as CONSTRUCTOR args, not
  as `chat(...)` call args. Call args are things like `stream=True`.
- `Chat(model)` picks the backend from the model id; force it with `runtime='llama'|'litert'|'remote'|'mlx'`.
